### 30.7a A stun clip that ends in a pose of its own is played once, not looped (maintainer report 2026-10-12, landed on the 自研 branch after 0.2.5) — `render/spine.js clipHoldsEnd` / `_playStun` / `_stunHolds`

**Seen**: a stunned model crouched and stood up again once per clip. 维什戴尔's `Stun` is the reported case; her clip's last
0.2 s drop the waist 98 skeleton units into the stunned crouch and leave it there, and `SpineActor` had played every stun
role as a loop (`_play(…, true)`) since it was written, so the cycle snapped back to the standing first frame every 1 s.

**`clipHoldsEnd(data, name, Skeleton)`** answers, from the skeleton itself, whether animation `name` ends in a pose of its
own: a scratch `Skeleton` (the same runtime class, `spine.skeleton.constructor`) is set to its setup pose and put through
the clip's own `apply` at t = 0 and at t = `duration`, and the two frames are compared bone by bone over position,
rotation and scale. Any bone further than `POSE_EPS` (5 units / degrees) apart means the clip ends somewhere else. That is
a per-clip **loop-mode** decision, not a flag carved into `data/assets.json`: a clip of that kind is played once and its
last frame stays on the track — the runtime clamps a finished non-looping track at its end, the same mechanism `die()`
uses — while a clip that ends where it started keeps looping. `false` for everything that cannot be inspected (an unknown
animation, a runtime shape without `apply`, a zero duration, a skeleton that cannot be sampled, a throwing
`findAnimation`), so an unrecognised model keeps the old looping behaviour. `SpineActor._stunHolds` samples each clip name
once and caches the answer.

**Affected models.** 维什戴尔 (`char_1035_wisdel`) and the other held-crouch stun clips — 引星棘刺 `char_1039_thorn2`,
W `char_113_cqbw` (front *and* back), 泡泡 `char_381_bubble` — now play their `Stun` once and hold. A seamless stun cycle
— 浊心斯卡蒂 `char_1012_skadi2`, 凯尔希·思衡托 `char_1052_kalts2`, 迷迭香 `char_391_rosmon` — still loops, and the same
hold/loop mode is carried through the `Stun_Begin` → `Stun` queue (`_playStun`) and through `setForm` (a 傀儡师's 替身
form's own stun clip). A stun role with no clip of its own still freezes the current track, and re-entering stun during a
stun remains a no-op (`_enterStun` returns while `mode === 'stun'`), so a per-frame `setBase('stun')` cannot restart the
clip.

**Tests**: `test/render/stun-hold.test.js` (untracked until this note) — the `clipHoldsEnd` comparison and its
unknown-shape fallbacks (`POSE_EPS` boundary included), the actor's once/hold vs loop choice, `Stun_Begin` queueing, the
no-clip freeze and the form switch, and — with `public/assets` present — the real roster's skeletons off
`data/assets.json` (维什戴尔 / 引星棘刺 / W / 泡泡 hold; 浊心斯卡蒂 / 凯尔希·思衡托 / 迷迭香 loop). Headless fake PIXI
(`test/render/fakepixi.js`). Recorded here because the fix predates this note: the file's own header carries only the
report date, 2026-10-12. Client-side only — `server/sim/` and `data/*.json` are untouched, so **no golden scenario moves**.

### 30.36 The 二次开发 version marker `0.2.5-E` (maintainer, 2026-10-13)

**What it means.** This tree is no longer plain upstream 0.2.5: it carries the maintainer's own layer (§29.15–§29.24,
merged with §30 by §30.31–§30.35c), so the release version is marked a **二次开发 (secondary-development) build** — `E`
for 二次开发, `0.2.5-E`. The marker is metadata only: no rule, no `data/*.json`, no `test/golden/*.json` digest, no i18n
pack entry and no `public/assets/**` file moved with it (measured: the version string reaches no digest — `golden.mjs`
never reads it).

**Two spellings, deliberately, and why.** `0.2.5-E` *is* a valid semver (a prerelease identifier may hold ASCII
alphanumerics), but semver's prerelease identifiers are **case-sensitive**. Measured on Node v24.15.0 with npm 11.12.1's
bundled semver 7: `valid('0.2.5-E') = '0.2.5-E'` (kept verbatim, not lowercased), `prerelease('0.2.5-E') = ['E']`, and
`eq('0.2.5-E','0.2.5-e') = false` — the two spellings are **not** the same version to any semver comparison.
`npm install --package-lock-only` on a probe package holding `"version": "0.2.5-E"` also exits 0 and writes the capital
back into `package-lock.json` unchanged. So nothing forces the lowercase; the repository follows the maintainer's ruling
and splits by audience:

- `package.json` and `package-lock.json` (`version`, and `packages[""].version`): **`0.2.5-e`** — the canonical
  lowercase prerelease spelling, so that every strict semver consumer and any future `npm version` / publish path sees
  one unambiguous value instead of a case variant.
- `shared/constants.js APP_VERSION` and every player-facing string — the title-screen footer, the boot banner,
  `/healthz`'s `app`, the README badge and its 简介 line: **`0.2.5-E`** — the maintainer's marker. The README badge
  escapes the hyphen the shields.io way: `badge/version-0.2.5--E-…`.

`test/version.test.js` therefore (a) accepts `-E` as the release marker, (b) normalises the case when it compares the two
package files against `APP_VERSION`, and (c) matches the CHANGELOG's newest `## x.y.z — date` heading against the numeric
core (`0.2.5`). `pkg.private === true`, `PROTOCOL_VERSION === 1` and the licence assertions are untouched.

**`DEV_BUILD` is unchanged.** It stays `/-dev$/.test(APP_VERSION)` — the public `dev` branch's *unstable, not for public
servers* flag that drives the title-screen 开发版 tag, the boot-banner warning, the top-of-README warning and
`tools/package.mjs --allow-dev`. `0.2.5-E` does **not** set it: no dev tag is drawn and the banner prints no warning.
The 二次开发 marker and the dev-build flag remain two separate things, and neither may flip the other.

**Packaging and release: affected, and in three concrete ways** (`tools/package.mjs` reads `package.json`'s version;
`isDevVersion` is `/-/.test(...)`):

1. **A release zip now needs `--allow-dev`.** `isDevVersion('0.2.5-e')` is true (any `-`), so `npm run package` and
   `npm run package:lite` refuse with 「`v0.2.5-e` is a development version」 unless `--allow-dev` is passed. That is the
   pre-existing behaviour for every prerelease and is the safe default — a 二次开发 build is not an upstream release.
2. **The artifact names carry `-e`.** With `--allow-dev`: `Stronghold-Protocol-v0.2.5-e.zip`,
   `Stronghold-Protocol-v0.2.5-e-lite.zip`, `Stronghold-Protocol-v0.2.5-e-update.zip`, the staging folder
   `Stronghold-Protocol-v0.2.5-e`, and `MANIFEST.json` / `UPDATE.json` with `app: "0.2.5-e"`.
3. **Two release-flow sharp edges, reported rather than silently changed.** (a) `releaseTag` strips only `-dev`, so
   player-document links are rewritten to `…/blob/v0.2.5-e/…` — a tag that does not exist unless the maintainer creates
   it; whether to tag `v0.2.5-e`, reuse `v0.2.5` or fall back to `releases/latest` is the maintainer's decision, so the
   code is untouched. (b) `tools/package-update.mjs compareVersions` follows semver's rule that a prerelease precedes
   its release, so `compareVersions('0.2.5','0.2.5-e') = 1`: passing the **upstream 0.2.5 full zip as an update base**
   is rejected with 「base 0.2.5 is not older than v0.2.5-e」. Building an update from a `0.2.5-e` full zip (to a later
   `0.2.5-e`-family version) is unaffected.

**Boundaries.** Version strings are the only files touched; `data/*.json`, `public/assets/**` and `test/golden/` are
untouched, `golden:update` was not run, and nothing was committed or pushed.
